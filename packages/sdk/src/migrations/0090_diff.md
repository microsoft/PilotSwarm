# Migration 0090 — user notifications for package reviews and broken cron prechecks

Informational only. Nothing in this migration changes review, activation,
binding, grant, admission or fencing state, and no existing row is rewritten.

## Added

- Table `user_notifications`: one row per recipient
  (`recipient_provider`, `recipient_subject`), with `kind`
  (`package_review`, `cron_precheck_broken`, `cron_precheck_recovered`),
  JSON `payload`, `occurrences`, `created_at`, `notified_at`, `last_seen_at`,
  `read_at` and `resolved_at`. `scope_key` groups a session's broken-precheck
  rows; `dedup_key` identifies one open broken row.
- Indexes: partial unique `user_notifications_open_dedup` on recipient and
  `dedup_key` while unresolved; `user_notifications_recipient` for listing;
  partial `user_notifications_open_scope` for recovery.
- `cms_notify_cron_precheck_broken(TEXT,TEXT,TEXT,TEXT,TEXT,TEXT) -> INTEGER`:
  session, precheck, outcome, package ID, version ID, digest. Rejects
  non-broken outcomes (only `error`, `timeout`, `invalid`, `unregistered`).
  Recipients are the session owner (direct owner, else the root session's)
  and the package owner only; editors and administrators are not notified.
  The package owner's copy omits the session ID. The payload carries package
  name, version, semver, digest, precheck, outcome and a fixed outcome summary;
  it never carries precheck detail text, tool output or secrets. Dedup is one
  open row per recipient, session, precheck, digest (or `worker`) and outcome.
  A repeat increments `occurrences`; after a day it re-notifies and marks the
  row unread again (daily reminder).
- `cms_resolve_cron_precheck_broken(TEXT) -> INTEGER`: resolves every open
  broken row for the session and inserts one `cron_precheck_recovered` row per
  resolved row for the same recipient, with the same visible fields plus
  `previousOutcome`, `brokenSince` and `brokenOccurrences`.
- `cms_package_review_notify()` and `AFTER INSERT` trigger
  `agent_package_review_notify` on `agent_package_review_audit`: an
  approve/reject/revoke that changes the decision notifies the package owner
  and editors in the same transaction, with the decision, previous decision,
  reason and revision. Failures are caught and raised as warnings, so a
  notification problem never blocks or rolls back the audited decision. The
  audit table's append-only trigger is unchanged.
- `cms_list_user_notifications(TEXT,TEXT,BOOLEAN,INTEGER)`: the caller's own
  rows only (authenticated principal required), newest first, limit clamped to
  1..200 (default 50). Approved review notices carry a live
  `approvedNotActive` flag, which clears when that version becomes active.
- `cms_mark_user_notifications_read(TEXT,TEXT,BIGINT[]) -> INTEGER`: marks the
  caller's own listed IDs, or all unread rows when IDs are `NULL`.

## Replaced

None.

## Schema and operations

Additive: one table, three indexes, one trigger and five functions. No
retention job is added; rows accumulate per recipient until a later cleanup
migration. Reapplying the migration is idempotent.
